dispatch and structure.**

### Corrections applied to this plan (two adversarial reviews overturned ten of its own claims)

Recorded because each was load-bearing and wrong. Every one came from measuring a proxy and
reporting it as the thing itself — a naive row regex, `cat *.go` that swept in tests, an import
grep that missed an interface field, a file read for row counts but not for its prose:

1. **The known-failure ledger was over-counted: 180, not 219.** And **NFS has more rows than SMB
   (92 vs 88)** — the reverse of what this plan first asserted.
2. **All per-directory LOC in the first draft were test-inclusive.** Corrected to prod-only below.
   `smb/handlers` is 34.4k prod, not 57.9k.
3. **The `smb/auth` split was unjustified** and is dropped — see "Target folder structure".
4. **#2395 does not land under the contended write lock** — `ValidateStateid` takes `RLock`. The
   claimed Wave 1 → Wave 2 dependency was a misdiagnosis and is removed.
5. **Wave 6 is already happening inside Waves 1 and 3** under other names.
6. **`CheckExportAccess` is a stale name, not a missing function** — the behaviour exists.
7. **SMB is NOT pinned to 1 credit.** Production selects `echo`, not `adaptive`; `smb2.credits`
   passes 10/10 and the known-failures file this plan parsed *says so in prose*. The broken
   `grantAdaptive` is dead by default. Called "the highest-leverage defect" in three drafts.
8. **The primary-GID consequence was mis-sited.** `file_access_checker.go:87` is SMB
   access-based-enumeration, not the NFS read path; the real read path already has the fallback.
   Symptom is a stripped SGID bit, fail-closed, low severity — not an access denial.
9. **`StoreIdentityResolver` is not a duplicate** of `ReverseResolver` — different contract, different
   data source. Unifying is a design change, not a dedup.
10. **Three sections (Identity, Tests, Instrumentation) were silently deleted** by a cleanup script
    during drafting and restored only because a review grepped for them. A plan that loses content
    without failing is the same class of defect as a test that passes against a broken build.

### Scope decisions (taken 2026-09-07, against a ponytail recommendation to cut)

A ponytail review argued the plan's real content is nine contained fixes (~1 page) and that the
remaining 85% is a refactor program generated by having 390 findings rather than by anyone being
blocked. It proposed cutting four of seven waves, keeping handler splits inside `package handlers`,
and leaving the pynfs wave with the peer session. **All three were overruled. Decisions:**

1. **Full program.** All seven waves proceed.
2. **Real package boundaries** — `smb/state/`, `handlers/create/`, `handlers/info/`.
3. **Full takeover** of the peer's NFSv4 stream, including #2398.

**Consequence of (2), and it is not optional.** `smb/handlers` has **119 in-package test files /
42,810 LOC** reaching unexported symbols. A same-package file split moves none of them; a package
boundary migrates all of them. So the Wave 5 apparatus — move-only PRs, `git diff -M --color-moved`
showing zero body edits, one package per PR merged same day, and a CI guard requiring a `_test.go`
in every new package — is **load-bearing under this decision**, not process theatre. It is the only
thing that keeps a 40k-line test migration reviewable. Do not drop it later as bureaucracy; it was
priced in when the boundary was chosen.

**Ponytail findings that survive the scope decision and are applied below:**

- `pkg/adapter/auxsvc/auxsvc.go` is **234 lines (125 non-comment)**, not the 411 stated twice in
  earlier drafts — the figure had swept in the test file. Third instance of the same measurement
  error in this plan.
- The accept-loop defect is confirmed verbatim at `pkg/adapter/base.go:246-263`: on a non-shutdown
  `Accept()` error it does `logger.Debug(...)` then bare `continue` — no backoff, no jitter, no

- Comment category 2 ("doc comments restating the signature") has **no mechanical grep** and

## The finding that reframes the work

**The shared layer already exists and both protocols route around it.** The work is deletion and
re-wiring, not construction.

- **`MapContentToNFS4` has zero production callers** (all references in
  `internal/adapter/common/errmap_test.go`). But the framing "broken on NFSv4 only" is wrong:
  **v3 READ (`read.go:134,185,268`) and v3 COMMIT (`commit.go:96-246`) also hardcode `NFS3ErrIO`.**
  Only v3 WRITE (`write.go:261`) calls `MapContentToNFS3`. **Five of six content paths bypass the
  shared mapper.** (`READ_PLUS` is at `v4/handlers/read_plus.go:121`.)
- **`MapLockToNFS3`/`MapLockToNFS4` have zero production consumers**, and 4 of 9 `lockErrorMap`
  rows duplicate `errorMap` byte-for-byte (`ErrLockNotFound`, `ErrGracePeriod`,
  `ErrPermissionDenied`, `ErrIsDirectory`). The reason deletion is *safe* is stronger than "unused":
  the NFS columns are **structurally unusable** — NLM speaks `nlm4_*` stat codes, and NFSv4 LOCK
  conflicts arrive as a structured `LOCK4denied` from the state manager (`lock.go:218-230`), never
  as a `merrs` error. Drift found in passing: `ErrLockLimitExceeded` maps to `Jukebox` in the lock
  map and `IO` in `errorMap`.
- **`CheckExportAccess` does not exist** as a symbol — only `CLAUDE.md:105` and a stale comment at
  `smb/handlers/create.go:1874` name it. The behaviour is real and lives in
  `internal/adapter/nfs/auth/share_permission.go` (`ResolveSharePermission`) and
  `smb/handlers/tree_connect.go:442`. **This is a rename in two places, not a function to write.**
- **Primary-GID derivation diverges**: NFS Kerberos → `BuildIdentityResolver` → `user.GID`
  (fallback 1000); SMB → `getUserIdentity` → first group with a GID (`auth_helper.go:101`, second
  site `handler.go:2038`). But the fix is a **deletion**: SMB Kerberos *already* resolves through
  `BuildIdentityResolver` (`pkg/adapter/smb/adapter.go:774,823`) and then throws the
  `ResolvedIdentity` away to re-derive from `models.User`. Delete `getUserIdentity`; don't unify it.
  **Scope the rule to *resolved* identities** — NFS AUTH_SYS takes UID/GID from the wire by design
  (RFC 5531), and must not be "unified".
- **`merrs.ErrConflict` has no `errorMap` row**; `errmap_test.go:54` hand-types a count of 25
  against an enum of 26 (`ErrConflict` at `errors.go:103`). Note the runtime coordinator wraps the
  ObjectID conflict into `engine.ErrObjectIDConflict` via `errors.Join`
  (`shares/coordinator.go:290-303`) — so the fix must **name which handler actually observes a
  `StoreError{ErrConflict}` and pin it with a test**, or "surfaces as a retry class" is aspirational.

### What NFS actually proves — and what it does not

The first draft said "give SMB the NFS shape". That copies NFS's *look*, not its shape, and
overstates the evidence:

- NFS handlers are **one package per protocol version, one file per op** (`v3/handlers`: 55 files,
  single package). Proposing ten command-family packages for SMB makes it **less** like NFS.
- NFS's layout contains the largest file in either adapter (`manager.go` 3,985) plus `open.go`
  1,103, `gss/framework.go` 942, `constants.go` 927, `encode.go` 896 — **six files over the 800
  ceiling this plan proposes**, and 142 verified findings with the same god-object and
  business-logic-in-handler shapes.
- Half of `v3/handlers` is `_codec.go` twins (27 pairs); every aux service carries a
  `handlers/types/xdr/` triad for a few hundred LOC. Conventions to **evaluate**, not inherit.

**NFS genuinely proves exactly two things. Copy these; treat the rest as open:**

1. The **two-tier `pkg/` shell ÷ `internal/` protocol split** — load-bearing, `cmd/dfs/commands/start.go`
   consumes both.
2. **`state/` separated from `handlers/`** — SMB has no state package at all.

## Handler design: what "simplified" means

### The five phases

| Phase | Does | Must NOT contain | Proven example |
| --- | --- | --- | --- |
| **Decode** | wire → typed request. Pure; no ctx, store, locks | business rules | `nfs/v3/handlers/write_codec.go` |
| **Validate** | structural checks (length, enum range, overflow) | store calls, ownership | `nfs/v3/handlers/write_validation.go` |
| **Resolve/Authorize** | handle-bound state, build `*metadata.AuthContext`, check the *protocol's own* grant (SMB `GrantedAccess`) | DACL/ownership evaluation | `smb/handlers/set_info.go:205-250` |
| **Delegate** | all domain logic via `pkg/metadata` | wire-format knowledge | `nfs/v3/handlers/write.go:236-276` |
| **Encode** | response → wire, errors via `common.MapTo*` | new decisions | `(*WriteResponse).Encode` |

SMB's handlers have these phases *braided into one basic block*. `set_info.go:284-682`
(`FileBasicInformation`, ~390 LOC) contains FILETIME sentinel decode, a domain rule about "frozen"
across four fields, a lock taken mid-function and released at three early-return sites, a store
call, and an ADS side-effect that re-calls `SetFileAttributes` on a *different* file.

### Patterns — adopt and reject

- **Dispatch table: already converged, add nothing.** SMB `dispatch.go:20-147`, NFSv3
  `dispatch_nfs.go:14-103`, NFSv4 `v40/v41/v42DispatchTable` (`v4/handlers/handler.go:68-81`).
- **ADOPT — hoist the duplicated post-dispatch block.** Two verbatim copies of ~90 lines
  (encryption check, channel-sequence check, four-command async-callback wiring) between
  `ProcessSingleRequest` (`response.go:197-263`) and `ProcessRequestWithFileIDAndCallback`
  (`response.go:568-624`). `prepareDispatch` is already shared; only the post half drifted.
  **−90 to −120 LOC, zero new types.**
- **ADOPT — copy NFSv4's params-struct**, not an invented template method: `dispatchOne`
  (`compound.go:128-184`) + `compoundLoopParams` (`:204-228`) already drive both 1-op and N-op
  COMPOUNDs.
- **ADOPT — `_codec.go` split** (NFSv3 convention). `create.go` is decode 201-326, contexts
  327-436, encode 437-498, handler 499-1528 in one file.
- **REJECT — middleware/decorator chain for the gates.** They are deliberately non-composable:
  CANCEL is exempt from the credit/sequence gate (`response.go:140`, MS-SMB2 3.3.5.16), ECHO from
  response ordering (`response.go:330`), and encryption must run after session but before
  channel-sequence (`response.go:198-214`). A chain re-encodes that ordering in the builder (no
  lines saved, one more layer) or hides it behind flags (worse).

### Naming

`handle*` currently means three things in SMB — dispatch trampoline, business sub-branch
(`handlePipeCreate`, `handleOpenRootCreate`, `handleSymlinkRead`), async entry (`handleOplockBreak`).
NFS uses it only for the trampoline. One verb, one job:

`Noun` = command entry · `handle*` = trampoline ONLY · `decode*`/`.Encode()` = wire · `validate*` =
structural · `verify*` = **cryptographic/security only** (keep a grep for it clean) · `resolve*` =
read-only lookup · `build*` = response assembly · `complete*` = second half of a `STATUS_PENDING`
op · `dispatch*` = per-op table resolution.

Renames: `handlePipeCreate`→`createPipeOpen` · `handleOpenRootCreate`→`createShareRoot` ·
`checkEncryptionRequired`→`validateEncryptionRequired` · `ProcessSingleRequest`→`dispatchSingle` ·
`ProcessRequestWithFileIDAndCallback`→`dispatchSubcommand` · `ProcessCompoundRequest`→
`dispatchCompound` · `storeCreateReplayIfApplicable`→`cacheCreateReplay` ("store" collides with the
metadata-store noun) · `updateBaseObjectTimestampsForADSWrite`→`propagateADSTimestampsToBase`.
Execute with `gopls rename`, never sed — dispatch entries and tests must move atomically.

### Debuggability — four concrete defects

1. **Step banners are comments, not stack frames.** `create.go` has 9 `// Step N:` banners inside
   one 1,030-line function; a debugger shows one frame. Make each a real call and the **stack trace
   becomes the step list**, which cannot drift from the code. This is a stronger argument for
   decomposition than LOC.
2. **Manual lock/unlock across early returns.** `set_info.go:404` takes `openFile.mu.Lock()`,
   released at `:486` and again at each later early return. Extract the region; use `defer`.
3. **Errors mapped with no phase context.** ~12 `common.MapToSMB(err)` sites in
   `setFileInfoFromStore` flatten which store call failed into a bare NTSTATUS, surviving only in a
   `logger.Debug` that is off in production. Wrap `fmt.Errorf("<op>: %w", err)` before mapping — no
   wire change, mapping still keys off `metadata.ExportError`.
4. **Observability stops at the top-level command** (RED metric at `response.go:23-40`). A
   `FileRenameInformation` doing ~9 metadata calls is one opaque sample.

### Worked example: `setFileInfoFromStore` (1,538 LOC)

Cases: `FileRenameInformation` ~645 · `FileBasicInformation` ~390 · `FileDisposition[Ex]` ~170 ·
`FileEndOfFile` ~110 · `FileAllocation` ~80 · `FileFullEa` ~57 · `FileMode` ~30 · `FilePosition` ~14 ·
`FileLinkInformation` ~5 (already a thin delegate — the model).

→ a ~25-line switch delegating to `set_info_codec.go` (~150), `set_info_basic.go` (~230),
`set_info_rename.go` (~550-600), `set_info_disposition.go` (~170), `set_info_size.go` (~200,
merging EOF/Position/Allocation), `set_info_mode.go` (~30), `set_info_ea.go` (~60).

Unverified: `renameFileOrDir` is estimated ~350-400 LOC and needs a further split once read in full.
The freeze/thaw timestamp semantics are an SMB concept with no NFS analogue, so that rule stays
adapter-side — the honest exception to invariant 1.

**Net LOC: flat.** Extraction is not deletion.

## Wave 2 — `sm.mu`, then the pynfs conformance wave (goal 1)

**#2398 decided first**, because #2341/#2340 add *write-side* work under the contended lock.

Criterion (settled, recorded on the issue): release-call-recommit is safe without re-validation when
the post-gap write is **idempotent, keyed by something stable, and records a fact the gap cannot
falsify**. `ReclaimComplete` (`manager.go:1348`) meets all three and is the sequencing precedent —
verified: keyed by `clientid_string`, a missing record makes the write a no-op (pinned cross-backend
at `storetest/client_recovery.go:288-296`), and its only reader (`client_recovery.go:202`) treats it
as history. A stateid/seqid commit meets **none**, so it owes the CAS. `RevokeDelegation` (`:1209`)
is only half the pattern — it discards its result and commits nothing.

Then, sized on `deb2d7b96`: #2341 (14 V40 rows) · #2340 (**32** V41) · #2329 (10 V41) · singles
#2371, #2382, #2389, #2399, #2359, #2362, #2369. #2399 is now a plain consumer of
`types/current_stateid.go`.

Count rows with `^\| *[A-Z]+[0-9]+[a-z]? *\|` — a trailing-digit regex drops `CSESS16a`,
`EID5c/5d/5f/5g`, `EID6a`–`EID6g`. Read verdicts from the **CI artifact**; the local pynfs harness
reports ~2× CI's failures on the same SHA.

## Scalability: does this hold thousands of connections?

**Honest answer: nobody has measured it, and there is no connection-scale test in the repo.** What
the code says:

- **NFS refuses connection 1025 out of the box.** `DefaultMaxConnections = 1024`
  (`pkg/adapter/nfs/adapter.go:46`) sizes a static `connSemaphore`. The accept loop acquires a slot
  *before* `Accept()`, so at the cap it stops accepting and new SYNs queue in the kernel backlog.
  Graceful, but silent and unlogged.
- **SMB has no cap at all.** `MaxConnections: 0 (unlimited)` (`pkg/adapter/smb/config.go:54`), and
  `preAcceptCheck` (`pkg/adapter/smb/adapter.go:565-585`) returns `true` unconditionally when it is
  ≤ 0. Two independent admission paths, both agreeing on unbounded.
- **This asymmetry — 1024 vs unlimited — looks unintended.** Flag it as a decision to make, not a
  setting to document.

**A real livelock, but "the first thing that breaks" was overstated.** The shared accept loop
(`pkg/adapter/base.go:246-262`) does `logger.Debug(...)` then bare `continue` on any non-shutdown
`Accept()` error — no backoff, no jitter, no `Temporary()`/`net.ErrClosed` classification. EMFILE
*is* persistent there: the kernel keeps the pending connection queued, `accept4` fails again
immediately, and the NFS semaphore is released and non-blockingly re-acquired, so it does not
throttle the spin. `net/http`'s `Serve` carries a 5ms→1s backoff for exactly this case; the fix is
~6 lines copied from it.

**But reaching it is harder than earlier drafts implied.** Go ≥1.19 (this tree is `go 1.25.0`)
raises `RLIMIT_NOFILE` soft→hard at startup, so on a stock Linux host NFS hits its 1024-slot
semaphore — which *blocks* in the `select`, no spin — long before EMFILE. SMB (unlimited) reaches
goroutine/memory pressure or the hard fd cap first. The spin needs a hard limit below the live
connection count: containers, or an explicit `ulimit -Hn`. Real, worth fixing, not the headline.

The `internal/adapter/nfs/doc.go` estimates ("~50MB baseline + 1MB × MaxConnections", ranges
"100-500" and "1000-5000") are **doc-author estimates with no profiling behind them.** Do not quote
them as capacity numbers.

### Goroutine lifecycle: the request paths are right, the sidecars are not

`pkg/adapter/nfs/connection.go` and `pkg/adapter/smb/connection.go` already implement the correct
discipline — spawn under a semaphore, track in a `WaitGroup`, `wg.Wait()` before teardown. SMB's is
the more careful of the two (it orders session teardown against an incoming connection's
SESSION_SETUP). **This is a consistency gap, not a design gap:** `pkg/adapter/nfs/udp.go:40-57`
launches two goroutines that nothing joins, and `udpSidecar.Stop` (`auxservices.go:177-182`) closes
the socket and returns without waiting for the read loop to observe it.

One rule, already proven in-tree: every long-lived goroutine is owned by one `WaitGroup`; `Stop`
cancels **and then waits**. Apply it to `startUDP`. No new machinery.

### TCP: resist adding more

Currently `SetNoDelay(true)`, `SetKeepAlive(true)`, `SetKeepAlivePeriod(15s)`. That is close to
correct and should mostly be left alone:

- **Do NOT add `SO_RCVBUF`/`SO_SNDBUF`.** The classic Samba `socket options` advice is now considered
  harmful by Samba's own maintainers — fixed buffers *disable* Linux's autotuning and cap the window
  below what a high-BDP link would otherwise reach. This is the cargo-cult option; its absence is a
  feature.
- `TCP_NODELAY` is already set, and is the one that historically mattered for request/response
  protocols (Nagle interacting with delayed ACKs).
- `IPTOS_LOWDELAY`/DSCP: irrelevant on switched LANs. Skip.
- **`SO_LINGER` is genuinely absent** and worth considering — for clean shutdown (last reply
  delivered before FIN), not throughput. *Unverified whether the existing drain discipline already
  covers it.*
- **Listen backlog is unset.** Combined with the accept-loop busy-loop, a reconnect storm after a
  partition heals is the realistic bad day. Backpressure, not wire tuning, is the lever.

What Samba and knfsd actually rely on at scale is multichannel, zero-copy I/O and kernel autotuning
— i.e. **flow control and admission, not socket options.**

### Flow control: SMB is broken, NFSv4.1 is sound

**NFSv4.1's `SlotTable` is correct** (`v4/state/slot_table.go`): `DefaultMaxSlots = 64`,
client-negotiated via `CREATE_SESSION4args` and clamped server-side (`session.go:96,100`), with
proper `SeqNew`/`SeqRetry`/`SeqMisordered` handling (`:154-210`) per RFC 8881 2.10.6. A genuine
positive — no credit-shaped defect to hunt.

One overclaim corrected: `SetTargetHighestSlotID` (`slot_table.go:285`) is defined and tested but
has **zero production callers**, so `sr_target_highest_slotid` is always static. That is an API, not
behaviour — do not cite it as evidence of dynamic slot signalling.

NFSv3/v4.0 have no session concept, so per-client parallelism is bounded by the per-*connection*
`requestSem` (default 100, shared across clients multiplexed on that connection). That is inherent
to those protocols, not a DittoFS defect.

**So per-connection parallelism today: NFSv4.1 → 64 slots (working) · NFSv3/v4.0 → 100 shared ·
SMB → the client's requested credits, up to 8192 (working, via the `echo` strategy).** The earlier
"SMB → effectively 1" claim was wrong; see the credits section.

## SMB credits: a broken strategy that production does not select

**This finding was overstated in three earlier drafts and is corrected here.** Two prior versions
called it "the highest-leverage defect in the audit" and claimed SMB is pinned to one in-flight
request per connection. **That is not true of any default deployment.**

`applyDefaults` (`pkg/adapter/smb/config.go:351-357`) sets `Strategy = "echo"`, with a comment
citing MS-SMB2 3.3.1.2 and Samba's `smb2_set_operation_credit`. The only production constructor,
`pkg/adapter/smb/adapter.go:163-165`, builds the manager with
`NewManagerWithStrategy(config.Credits.GetStrategy(), ...)`. `grantEcho` returns the client's
`requested` clamped to `[MinGrant=1, MaxGrant=8192]` — a Windows client asking for 128 gets 128.

`NewManager` → `StrategyAdaptive` (`manager.go:33`) is reachable only via `NewDefaultManager`
(`manager.go:54`) ← `handlers.NewHandler()` (`handler.go:1016`), and **`NewHandler()` has no
production callers** — test-only.

**The tree already said so, in a file this plan read for other reasons.**
`test/smb-conformance/smbtorture/KNOWN_FAILURES.md:155-163` states that credit arithmetic is correct
post-#399/#416 and **the full `smb2.credits` subsuite (10 tests) passes.** The plan parsed that file
for row counts and never read its prose. That is the failure mode of checking whether data *bears*
on a question before citing it — the disconfirming evidence was already open.

### What is still a real defect

`grantAdaptive` (`manager.go:231-292`) is genuinely broken, exactly as read:
`baseGrant := float64(InitialGrant)` = 1; factors are multiplicative, max ×1.5; `uint16(1.5) == 1`;
`MaxGrant = 8192` is unreachable; and `requested` is consulted only to clamp *downward*
(`if requested > 0 && requested < grant`) under a comment claiming "echo behavior within adaptive".

Two ways a deployment reaches it:

1. An operator explicitly sets `strategy: adaptive`.
2. **An operator typos the value.** `GetStrategy()` (`config.go:398-410`) maps every unrecognised
   string to `StrategyAdaptive` — so `strategy: adaptiv` silently selects the broken branch. The
   `default:` arm should return `StrategyEcho`, matching `applyDefaults`.

`StrategyFixed` is `iota` = 0 (the Go zero value) and returns `InitialGrant` flat — also 1.

**Fix (lazy version, preferred): delete `StrategyAdaptive` and `StrategyFixed`.** Two strategies
that are dead by default, one of them known-broken, and a config surface whose invalid-value
fallback selects the broken one. `grantEcho` is what production uses, matches Samba, and passes
conformance. If the adaptive idea is wanted later, it can be rebuilt against a benchmark rather than
resurrected from a branch nothing exercised. Also fix the `default:` arm before deleting, in case
the deletion is deferred.

**Do NOT raise `InitialGrant`.** It is 1 deliberately: a previous 256 (boosted to 384) overflowed
Samba's client-side `uint16_t cur_credits` during rapid SESSION_SETUP/LOGOFF cycling, producing
`NT_STATUS_INVALID_NETWORK_RESPONSE` (`credits.go:12-18`, issue #378, citing
`libcli/smb/smbXcli_base.c:4295-4298`).

### Consequences for the rest of this plan

- The "per-connection parallelism today" line in the scalability section must read **SMB → the
  client's requested credits, up to 8192** — not "effectively 1".
- Measurement #3 (SMB pipeline depth vs throughput) predicted flat throughput beyond depth 1. **That
  prediction is withdrawn.** The test is still worth running as a baseline, but as characterisation,
  not falsification.
- This is no longer a Wave 7 headline. It is a small correctness-and-deletion item in Wave 3.
## Buffer pool: fix the sizing, do not generalize

**Do not move it out of `internal/adapter/pool`.** A grep of `pkg/block` for raw `make([]byte, ...)`
in non-test files finds none — the block layer follows the streaming-I/O convention and reads/writes
into caller-supplied buffers. Only **6** files import the pool, all in the adapter layer (`common/read_payload.go`,
`nfs/connection.go`, `nfs/v3/handlers/read.go`, `smb/framing.go`, `pkg/adapter/nfs/connection.go`,
`pkg/adapter/smb/connection.go`). Generalizing
solves a problem that does not exist.

**Keep the `globalPool` singleton.** `sync.Pool` is already per-P internally with a victim cache;
sharding per-adapter or per-share would fragment hit rate without buying isolation, since buffers are
`Put` before crossing any boundary.

**The sizing is the actual bug, and it is worse than "the tier equals the default max I/O":**

- Tiers are 4KB / 64KB / **1MB** (`bufpool.go:43,46,49`); `Get(size)` above the large tier does a bare
  `make([]byte, size)` — straight to GC.
- Operators can configure max read/write size up to **16MB** (`adapter_settings.go:363,365`), a
  supported control-plane operation. Any deployment that does so sends **100% of large I/O around the
  pool**, both protocols, both directions.
- **Even at the default it already misses**: `MaxFragmentSize = (1<<20) + (1<<18)` — 1MB + 256KB of
  RPC/XDR headroom (`internal/adapter/nfs/connection.go:24`) — exceeds the 1MB tier, so a max-size
  NFS WRITE falls off the pool today, unconfigured.

Fix the tier to the real ceiling plus framing headroom (`16<<20 + 1<<18`), or derive it from the
adapter's negotiated max at construction. `sync.Pool` grows lazily, so this does not inflate
steady-state memory for small-I/O deployments. **Check `Put`'s size classification first** — retiering
without capping what is *retained* would start holding 16MB buffers across GC cycles.

Two related bypasses, lower priority:

- **NFSv4 READ never clamps against the advertised max read size** (`v4/handlers/read.go:121-137`),
  clamping only against file size — while v3 (`v3/handlers/read.go:228-253`) and SMB
  (`smb/handlers/read.go:242-246`) both do it correctly. A v4-specific regression; add the clamp its
  siblings already have.
- **SMB allocates twice on inbound read**: `framing.go`'s `readNetBIOSPayload` does an unpooled
  `make([]byte, msgLen)`, then `Serve()` copies the body into a *second*, pooled buffer. NFS's
  equivalent does one pooled read.

## auxsvc: keep it, rename it, fix the lock

**Keep the abstraction.** `Service`/`Group` is **234 lines (125 non-comment)**, one file, a 3-method
interface, tearing down in reverse registration order (preserving "unregister from rpcbind before closing the portmapper"), and
every wrapper in `auxservices.go` is a 1-3 line shim. Splitting it would be ceremony. (Earlier drafts said 411 LOC — that included the test file.)

**Rename `auxsvc` → `sidecar`** (kept under the full-program decision; ponytail argued to cut it as
churn — 47 references across 9 files, and it will conflict with any in-flight peer branch touching
`pkg/adapter/{nfs,smb}`. Sequence it when no such branch is open). The drift is one-directional: every implementation already calls
itself a sidecar — `portmapSidecar`, `sysregSidecar`, `udpSidecar`, `nsmSidecar`, plus
`mdns.Sidecar`, asserted against the interface at `auxservices.go:205`. The package is the only
place still using "auxiliary service" vocabulary, and its own doc comment describes "companion
services" without ever using the word `auxsvc`. Pure rename.

**Fix the lock.** `Group.Start` (`auxsvc.go:96-114`) calls `s.Start(g.baseCtx)` at `:107` while
holding `g.mu`. Every other `Group` method takes the same mutex, and `startEnabledAuxServices` runs
inline in the NFS `Serve` startup path before the accept loop begins — so a slow `sysreg` start
against an unreachable rpcbind delays shutdown, settings reconciliation, **and the accept loop
itself**. Reserve the name slot under the lock, release, call `Start` unlocked, re-acquire to confirm
or roll back. Standard critical-section shrink; the same shape as #2398's.

### Primary GID — corrected: narrower than earlier drafts claimed

`HasGID` scans only `GIDs` (`pkg/metadata/auth_identity.go:222-224`) — confirmed. But "the primary
GID is never appended" is true of **only one** producer:

- **True**: the store-backed `userLookup` closure in `pkg/adapter/identity.go` builds `gids` from
  `user.Groups` + SID mappings and never appends `user.GID`.
- **False for LDAP**: `resolveGroupGIDs` puts `primaryGID` first (`pkg/identity/ldap/provider.go:644-660`),
  and its comment describes exactly this bug.
- **False for SMB**: `synthUserFromResolved` lists primary first (`kerberos_auth.go:552-560`), and
  `getUserIdentity` derives the GID *from* `Groups`, so it is present by construction.

**The consequence was also mis-sited.** `file_access_checker.go:87` is not the group-class read
path: `CheckAttrReadAccess` has one caller — SMB access-based enumeration
(`query_directory.go:1215`), POSIX fallback only when the entry has no ACL. Its effect is hiding a
directory entry from an SMB listing; an NFS Kerberos user never reaches it. The real read path,
`calculatePermissions` (`auth_permissions.go:367`), **already** does
`*gid == attr.GID || identity.HasGID(attr.GID)`, as does `file_modify.go:468`.

Reachable symptom, for a store-backed NFS Kerberos user whose `user.GID` is not in `user.Groups`:
**the SGID bit is silently stripped** on create (`file_create.go:340`) and chmod
(`file_modify.go:404`). Fail-closed, low severity — not an access denial.

**Fix is one line**, closing all three inconsistent sites without touching any resolver:

```go
func (i *AuthIdentity) HasGID(gid uint32) bool {
    return (i.GID != nil && *i.GID == gid) || slices.Contains(i.GIDs, gid)
}
```

No existing test covers the primary-only case: `query_directory_abe_test.go:22-37`'s `authForUID`
puts `gid` in both `GID` and `GIDs`, masking it.

### Three resolvers, one stale cache

`BuildIdentityResolver` is called at exactly three sites: `pkg/adapter/nfs/nlm.go:733`,
`pkg/adapter/smb/adapter.go:774` (subscribes `OnIdentityMappingChange` at `:784`), and
`pkg/adapter/smb/adapter.go:823` — which subscribes only `OnIdentityProviderConfigChange` and
**never `OnIdentityMappingChange`**. So an identity-mapping edit refreshes the session-auth resolver
and leaves the foreign-SID display resolver stale for up to the 5-minute TTL.

Fix: build **one** resolver per runtime (a runtime field, like `ldapConfig` at `runtime.go:217-221`),
exposed via `rt.IdentityResolver()`. The missing subscription then cannot exist. Caches go 3 → 1.

**Correction to an earlier draft**: `internal/adapter/smb/rpc/identity.go`'s `StoreIdentityResolver`
is **not** a duplicate of `ReverseResolver`. Different contract and different data source —
`ReverseResolver.LookupUID(ctx, uid) (name, domain, ok)` is a provider capability implemented only
by LDAP (`provider.go:353`), answering from the directory; `StoreIdentityResolver` is a ctx-less
closure pair over `cpStore.GetUserByUID`. The pipe manager already consumes both
(`adapter.go:325`, `:832`). Unifying them means writing a store-backed provider that implements
`ReverseResolver` — a design change, not a dedup. **Do not fold this into Wave 3.6.**

Also: `userLookup` (`pkg/adapter/identity.go:37-85`) returns `Found: true` on any store hit with **no
`Enabled` check**, while SMB re-derives its own gate at `kerberos_auth.go:587-596`. That SMB must
re-check on top of the shared resolver is itself the argument for putting it in `userLookup`. NFS
krb5 has no such gate. And `:45,49` fabricate UID/GID `1000` when unset.

**Wave 3.5 correction**: "delete `getUserIdentity`, SMB already has the `ResolvedIdentity`" holds
**only for the Kerberos path**. `buildIdentity` (`auth_helper.go:159→187`) and `handler.go:2038`
call it on a `models.User` — the NTLM/local-user path, which never passes through the resolver
because there is no `Credential` to resolve. Deleting it requires a replacement for that path.

**`docs/guide/smb-acl-fidelity.md` is NOT stale** — `BuildSecurityDescriptor` (`security.go:291`),

## Tests

`pkg/adapter` sits at **0.57** test:prod and holds 3 of the 6 core-audit HIGHs. The gap is
concentrated, not spread: **`pkg/adapter/identity_test.go` does not exist**, so the function every
SMB and NFS Kerberos session calls has zero unit coverage. That is why the `Enabled` bypass
survived — its only coverage is transitive, through slow e2e Kerberos tests.

A 1.0 ratio proves nothing about whether a test can fail:

- `errmap_test.go:20-47` hand-types 25 codes and `:53-56` asserts `len(...) == 25`; `ErrConflict`
  is simply absent, so the test **cannot** see the drift.
- A whole suite once passed green, `-race` included, while the real rig wedged — fake sinks.
- Postgres tests are all `//go:build integration`; `go vet ./...` does not compile them without
  `-tags integration`.

**Boundary**: unit for pure logic (error mapping once enum-derived, the SID codec, ACL evaluation,
the resolver chain with fake providers); integration for anything touching a real backend, where
faking hides the bug class; e2e only for genuinely cross-protocol assertions. The `Enabled` bypass
is the example — a unit test on `BuildIdentityResolver` would have caught it faster than the e2e
Kerberos test that didn't.

**Delete**: tests for the dead NFS mappers (`convention_test.go`, `table_test.go`, `cache_test.go`)
— real passing tests for dead code. Plus any benchmark whose setup sits inside the timed region
(the 57-vs-28,484-iteration case): not false, just non-comparable, and therefore useless as a gate.

**Enforce** (load-bearing under the package-boundary decision): a new package under
`internal/adapter/smb/handlers/` with zero `_test.go` files fails CI.

## Instrumentation

**An earlier draft claimed the adapters were uninstrumented. That was false.** Both protocols
already record RED metrics at exactly the dispatch seam this plan would otherwise have proposed
building:

- SMB: `internal/adapter/smb/response.go:23` (`recordRequest`), from `:111` and `:547` — one
  function, three callers, labels precomputed at `init()` to keep the hot path allocation-free.
- NFS: `pkg/adapter/nfs/handlers.go:44` (`recordOp`), from six sites
  (`:144,:203,:272,:388,:462,:525`).
- `pkg/adapter/base.go:292,320` records connection accept/close for both.
- `RecordAuth` is wired on both sides (`nfs/dispatch.go:70`, `smb/handlers/session_setup.go:32`).

The original search failed because these reach metrics through a **narrow interface field**
(`connInfo.Metrics`, `Registry.Metrics()`; declared at `internal/adapter/smb/conn_types.go:29`)
rather than importing `pkg/metrics`. That is better Go — interface declared at the consumer — and
invisible to an import grep. *An absent import is not an absent behaviour.*

Cardinality is already correct: `{protocol, op, status}` with status bounded to `ok|error` and a
static `op` set from the dispatch table. Any new label must follow it.
