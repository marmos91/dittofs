- **What:** handleOpenClaimNull's new-file branch (open.go:427-455) builds newAttr := &metadata.FileAttr{Mode, UID, GID} from effectiveUIDGID + createAttrs.Mode only, then calls metaSvc.CreateFile(authCtx, parentHandle, filename, newAttr). Any other field the client set in createattrs — Size, Atime/Mtime (SET_TO_CLIENT_TIME4), ACL, Hidden, etc. (all present on metadata.SetAttrs, file_types.go:199-219) — is decoded into createAttrs but never applied: metadata.CreateFile's signature only accepts *FileAttr (Type/Mode/UID/GID/Size/Nlink/times as a flat attr snapshot, not the client's SetAttrs bitmap), and no follow-up SetFileAttributes/applySetAttrsWithTruncateReclaim call is made for the newly-created file. Contrast with the adjacent existing-file UNCHECKED4 branch (open.go:407-426), which explicitly calls h.applySetAttrsWithTruncateReclaim(ctx, metaSvc, authCtx, fileHandle, child, createAttrs) to apply the *full* createAttrs bitmap — the new-file path has no equivalent call.
- **Why it matters:** RFC 7530 §16.16.4: for UNCHECKED4/GUARDED4 (and RFC 8881 §18.16.4 for EXCLUSIVE4_1's cattr), createattrs sent by the client 'MUST be applied atomically with the object creation' — the server must honor every attribute in the bitmap, not just mode. Dropping owner/times/ACL/hidden attrs at create means a client that creates a file with e.g. an explicit mtime, ACL, or hidden bit gets a file silently missing those attributes with no error returned (the OPEN succeeds NFS4_OK), which is a spec-conformance regression relative to nfs-ganesha/knfsd (both apply full createattrs at create) and inconsistent with this same handler's own existing-file UNCHECKED4 code path one branch away.
- **Fix:** After metaSvc.CreateFile succeeds, apply the remaining createAttrs fields (anything beyond Mode/UID/GID — Size, Atime/Mtime, ACL, Hidden) via the same applySetAttrsWithTruncateReclaim/SetFileAttributes path already used for the existing-file UNCHECKED4 branch, so newly-created files honor the client's full createattrs bitmap.
- **Verified:** CONFIRMED. open.go new-file branch builds newAttr = &metadata.FileAttr{Mode, UID: uid, GID: gid} (+IdempotencyToken for the verifier) and calls metaSvc.CreateFile; no applySetAttrsWithTruncateReclaim / SetFileAttributes follow-up, unlike the existing-file UNCHECKED4 branch one block above which does apply the full createAttrs bitmap. So client-set size/atime/mtime/ACL/hidden in createattrs are decoded and dropped. Reachable: register_v40.go:43 OP_OPEN -> handleOpen. Reference impl: knfsd nfsd4_decode_createattrs fills op_iattr (ATTR_SIZE/ATIME/MTIME/MODE) and nfsd_create applies it. Mitigation that caps severity at MED: open.go:709 encodes attrset as an empty bitmap, so the server does not falsely claim it set them, and the attrs real clients send at O_CREAT (mode) ARE applied; size=0 on a fresh file is a no-op.
