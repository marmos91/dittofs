# #1872 block packing — rig results (2026-08-24)

Two A/B runs against S3 on one Scaleway VM, plus a third after a hang fix.
Object counts come from diffing the bucket listing against a pre-run snapshot,
so they are exact rather than sampled. Raw listings and server logs are not
committed — the project ignores run output everywhere else it produces it.

## Setup

- One VM per session, `POP2-8C-32G`, `fr-par-1`, ubuntu_noble, 50 GB data volume.
- Harness pinned to `origin/develop` on both sides, so an A/B differs only in the
  server binary. Both binaries built `linux/amd64`, `CGO_ENABLED=0`.
- Probe: `dittofs-s3-writeback-nfs3`, `--workloads seq-read,rand-write-4k`,
  `--skip-baseline --runtime 60 --threads 4 --evict-cache`.
- `PutBlock` is one `PutObject` under `blocks/<blockID>`, so an object's `Size`
  **is** its PUT size. Runs are separated by `LastModified`.

## Results

| | develop | packed (pre-fix) | packed (fixed) |
|---|---|---|---|
| objects | 20,391 | 52 | 795 |
| median size | 4,168 B | 4,226,761 B | 4,227,316 B |
| objects per MiB | 165.8 | 0.259 | — |
| drain | 1035 → 924 MiB | 30 identical samples | 1322 → 628 → 88 → 0 |
| write p99 | 123 ms | 2.26 s | 41.2 ms |

develop's distribution is entirely `4096n+72` — 13,861 objects at 4,168 B and
4,114 at 8,264 B. That is run-length quantisation: blocks were cut at each dirty
run's end, and scattered 4 KiB writes make every run tiny.

The fixed run's drain reaching zero cross-checks two ways: 1,420 objects landed
for the bytes written, and `completed_syncs` plus drain attempts equals that
object count exactly.

## Caveats that bound these numbers

- **No fresh develop control for the third run.** Its comparator is the earlier
  run, on a different VM ~90 minutes earlier, and the cells started from
  different unsynced states. The write-path figures are therefore not a clean
  A/B: they support "the 2.26 s tail is gone", not a speedup ratio.
- One run per cell. Only the object sizes are exact; everything else is a single
  observation.
- The third run's scattered window includes some layout-drain carryover, so it
  is "the scattered window", not "what random writes alone produced".
- `dfsbench setup` stalled in `waitSSH` (the 1Password agent will not sign for
  ssh invoked from a tool), so the remaining setup was completed by hand against
  the same VM, replicating `prereqs.go` with binary hashes verified on the box.

## Reproducing

Snapshot the bucket before and after a run and diff the keys, then histogram the
sizes:

```bash
aws s3api list-objects-v2 --bucket "$BUCKET" --prefix blocks/ \
  --query 'Contents[].[Key,Size,LastModified]' --output text > before.tsv
# ... run the probe ...
aws s3api list-objects-v2 --bucket "$BUCKET" --prefix blocks/ \
  --query 'Contents[].[Key,Size,LastModified]' --output text > after.tsv
comm -13 <(cut -f1 before.tsv | sort) <(cut -f1 after.tsv | sort) > new-keys
```

Bucket a run's sizes by joining `new-keys` against `after.tsv` and counting into
power-of-two buckets. Select a run's window by `LastModified` rather than by
wiping the bucket — a `--recursive` delete runs at roughly 3k objects/min and
will overlap the next run's uploads.

## What this did not settle

- The cold barrier still fails, now because the drain reaches zero and the call
  observing it does not return (#2090).
- `ManifestRowEndAfter` scans the whole manifest per call. That cost is
  pre-existing and shows on both sides of the A/B, so it is not the mechanism
  #1872 describes and did not stop this drain: 2220 MiB reached zero in ~110 s.
  It is carried as a `ponytail:` note on the lookup and on the run-extension
  that calls it, to be sized from a profile rather than guessed at.
- Packed commits touch far more non-adjacent keys than a scattered develop
  commit for the same bytes.
